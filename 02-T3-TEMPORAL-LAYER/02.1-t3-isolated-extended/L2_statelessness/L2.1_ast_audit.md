**Date:** 2026-05-09
**Audit method:** Two passes of AST walk over `Musical_Intelligence/ear/h3/`:
1. **Compute-method scan** — flags `self.X = ...` and `global` in 8 named compute paths (extract / compute / forward / __call__ / step / process / apply / run / transform / compute_weights / execute / select / build).
2. **Strict scan** — flags ANY `self.X = ...` (Assign / AugAssign / AnnAssign) outside `__init__` / `__post_init__` across **all class methods** (not just compute paths). Catches helper-method state mutations that the compute-method scan would miss.

No `self._ema`, no `self._previous_output`, no `self._count`, no `self._cache`, no `self._buffer`, no `self._history`, no `self._accumulator`, no `self._last_*` exists in any compute path.

## Class-construction observation

The 15 classes split structurally:

- **Stateless utilities** (no `__init__` body, or `__init__` only stores immutable config): `AttentionKernel`, `MemoryWindow`, `PredictionWindow`, `IntegrationWindow`, `WarmUpHandler`, all four `*Band` classes, `EventHorizon`. These are pure-function objects.
- **Frozen dataclass**: `H3Output` — assignment to fields raises (verified at L12_api when populated).
- **Construction-only state**: `H3Extractor`, `H3Executor`, `MorphComputer`, `DemandTree`. These set immutable config in `__init__` and have no `self.X = ...` mutation in any other method.

This pattern means: **two `H3Extractor.extract()` calls on the same input produce bit-identical outputs by construction** — the AST audit proves there is no internal state to drift between calls.

## Anti-pattern probes (also clean)

The audit specifically searched for these state-keeping idioms; **all returned zero hits**:

- `self._ema` / `self.ema_*` (exponential moving averages)
- `self._previous_output` / `self._previous_value` / `self._previous_state` / `self._prev_*`
- `self._count` (incremental counters)
- `self._cache` / `self._cache_*`
- `self._buffer` / `self._buffer_*`
- `self._history`
- `self._last` / `self._last_output` / `self._last_value` / `self._last_call`
- `self._accumulator` / `self._accum`
- `self._running_mean` / `self._running_sum` / `self._running_var`
- `self._memo`
- `self._state`

## Strongest implication

The combination of these two passes establishes T³'s **embarrassingly-parallel property as a structural consequence of the source code**: because no method on any class mutates instance state after construction, frame-by-frame computations are independent. This is the load-bearing assumption behind the bit-determinism claim measured in L3 (`determinism_canary`).
